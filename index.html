Meal Prep & Meal Plan Shopify 2.0 Theme — Version 1.4

Prep Meal – Meal Prep & Meal Plan Shopify Theme

Prep Meal is a Shopify Online Store 2.0 theme built for weekly meal-prep businesses: meal plans with a slot-based box builder, a weekly rotating menu, a delivery-area checker with a live map, gift cards, private-chef bookings, and a full set of editable sections.

Theme Features:
  • 31 ready JSON templates (home, meal plans, products, contact, delivery, gift cards and all Shopify system pages)
  • 85 sections and 58 snippets — every section editable in the theme editor
  • Meal plans in 5, 6, 7, 10 and 15 plate variants
  • Slot-based “Build your box” with 5-plate / 10-plate discount tiers
  • Weekly menu with hover previews, nutrition facts and meal details
  • Metaobject driven content (meal plans, FAQ, testimonials, steps, delivery zones) with block fallback
  • Delivery-area checker with town/ZIP search and Leaflet map
  • Gift card purchase flow with recipient, delivery date and message
  • Private chef experience page with enquiry form
  • Ajax cart drawer, predictive search, quick order list
  • GSAP scroll animations with reduced-motion support
  • Cart drawer, filters, localization and customer account pages included
  • Translation-ready locales, accessible markup, lazy-loaded imagery

Requirements

  • Shopify plan: Basic or higher. Online Store 2.0 themes require a plan that includes the theme editor.
  • Theme version: Online Store 2.0 (JSON templates). Do not install on a vintage 1.0 store.
  • Products: A product per meal plan (for example 5-meal-plan) whose variants are the individual meals.
  • Optional: A gift card product, and a Shopify plan that supports gift cards, for the gift card page.
  • No apps required. Every feature — box builder, delivery checker, gift card flow — ships in the theme.
  • Browser support: Chrome, Firefox, Safari, Edge (latest two versions), iOS Safari and Chrome for Android.
No coding needed. Install the theme, connect your products and metaobjects, and fill the sections in the theme editor. Code editing is only required if you change the design system itself.

Theme Installation

Option A — Upload the ZIP (recommended for first install):

  1. In Shopify admin go to Online Store → Themes.
  2. Click Add theme → Upload zip file and choose prepmeal-shopify.zip.
  3. Wait for the theme to upload, then click Customize to preview it.
  4. When you are happy, click Publish to make it the live theme.

Option B — Shopify CLI (recommended for development):


# Log in to the store you develop against
shopify theme dev --store your-store.myshopify.com

# Push all files to a new unpublished theme
shopify theme push --store your-store.myshopify.com --unpublished

# Later: push only the files you changed
shopify theme push --store your-store.myshopify.com --theme 123456789 --only sections/cm-build-box.liquid

After installing, do these four things in order:

  1. Upload your logo and favicon in Theme settings → Logo.
  2. Create the menus under Content → Menus (main menu, footer menu) and select them in the header and footer sections.
  3. Create your metaobject definitions and entries (see Metaobjects).
  4. Assign the meal plan templates to your pages and products (see Templates & Pages).
Keep a backup. Use Online Store → Themes → … → Duplicate before you edit the live theme, so you can always roll back.

Fonts Used

By default the theme loads these Google Fonts:

  • Jost — body text (400, with bold and italic variants)
  • Plus Jakarta Sans — headings (700)

The font link is in layout/theme.liquid:


<link rel="preconnect" href="https://fonts.googleapis.com">
<link rel="preconnect" href="https://fonts.gstatic.com" crossorigin>

The CSS variables that every section uses are defined in the :root block of the same file:


:root {
  --font-body-family: "Jost", sans-serif;
  --font-body-style: normal;
  --font-body-weight: 400;
  --font-body-weight-bold: 700;

  --font-heading-family: "Plus Jakarta Sans", sans-serif;
  --font-heading-style: normal;
  --font-heading-weight: 700;

  --font-body-scale: 1;
  --font-heading-scale: 1.1;
}
Important: the heading font is set directly in layout/theme.liquid. The Heading font picker in Theme settings loads the font file, but the visible heading font comes from --font-heading-family. To change headings reliably, change both — the picker for the file, and the variable for the rendered font.

To use a completely different typeface, replace the Google Fonts link, then update --font-body-family and --font-heading-family. Section CSS reads those variables through --prep-font and --prep-display in assets/prep-content.css.

Step 1 — Change the kitchen position

Open the theme editor, go to any meal plan page (/pages/5-meal-plan … /pages/15-meal-plan), select the CM meal plan page section and scroll to Delivery checker: map.

Easiest way — type the place name. Put a place in Kitchen latitude or place name (delivery_kitchen_lat) and leave the longitude alone. The theme looks the place up when the page loads and puts the pin, the delivery circle and the map centre there.


delivery_kitchen_lat = Hartland, Wisconsin     ← place name is enough
delivery_kitchen_lng =                        ← leave blank

You can be as loose as a town name or as precise as a full street address. Country-aware names resolve more reliably:


Waukesha
Waukesha, Wisconsin
N64W28381 Hawthorne Rd, Hartland, WI 53029

Exact way — use coordinates. Numbers always win over a lookup and skip the network call entirely:

  1. Set delivery_kitchen_lat to your latitude.
  2. Set delivery_kitchen_lng to your longitude.
  3. Set plate_kitchen_address to the address text you want shown, for example Waukesha, Wisconsin.
  4. Leave delivery_radius_km at 0 to auto-fit the zone circle to your farthest town, or set a fixed radius in km.

Latitude and longitude are decimal degrees, not degrees/minutes/seconds. Latitude is positive north of the equator, longitude is negative west of Greenwich — so a Wisconsin address is always lat positive and lng negative.

Place names in one field, numbers in the other. The theme decides by looking for a number. If the latitude field holds a word, it treats the pair as a place name and looks it up. If it holds a number, both fields are read as coordinates. Never mix a name into the longitude field.
Optional country hint. delivery_country narrows lookups when a town name exists in several countries — for example Hartland exists in both Wisconsin and Devon, England. Set it to United States, United Kingdom and so on.
Step 2 — Change the delivery towns

Name-only rows are enough. Write one town per line. If you leave the coordinates off, the theme finds the place for you:


Hartland
Delafield
Waukesha|53186,53188,53189
Pewaukee

The format is Name|ZIP,ZIP. Everything except the name is optional:

You type What happens
WaukeshaName only. The point is looked up automatically.
Waukesha|53186Name and ZIP. Point looked up, and customers can search by postcode.
Waukesha|53186,53188Several ZIPs for one town, comma separated, no spaces.
Waukesha|43.0117|-88.2315|53186Exact coordinates. Skips the lookup and is always fastest.
  • Paste the list into Delivery towns (delivery_towns).
  • Leave the field empty to keep the packaged Hartland / Lake Country list. An empty field never means “no delivery areas” — it falls back to the built-in list.
  • delivery_initial_chips controls how many towns show as buttons before “Show all”.
  • A town that cannot be found still appears as a searchable chip and still answers “yes we deliver” — it simply gets no pin on the map. Give it coordinates if you want it plotted.
  • Names resolve near your kitchen, not worldwide. The lookup is biased to the kitchen position so that Sussex finds Sussex, Wisconsin rather than Sussex, England. If a town still lands in the wrong place, add its state to that row — Sussex, WI.

The plate map takes the same idea with its own column order:


Name|ZIP,ZIP|left%|top%|kitchen|lat|lng
  • Only the name is required. Hartland|53029|41|29|kitchen works with no coordinates at all.
  • Add the word kitchen as the fifth column on the row that marks your base.
  • lat and lng (sixth and seventh columns) are optional. Towns that already exist in the theme's built-in coordinate table work without them; any other town is looked up by name.
  • left% and top% (third and fourth columns) are optional leftovers from the older stylised plate. Pins are now placed from real coordinates, so you can leave these out on new rows.
  • plate_zone_radius is kept for compatibility with older lists. The ring now fits itself to your farthest town, so leave it at its default.

The plate map is a styled street map, not a drawing. It renders real OpenStreetMap tiles, so towns, roads and labels are always in the right place — you never have to eyeball a position. The map opens framed on your kitchen with the delivery ring around it, and the town chips sit alongside it.

The marked town wins over the kitchen setting. The plate map centres on delivery_kitchen_lat and delivery_kitchen_lng, but if one of your plate_towns rows carries the word kitchen, that town's position is used instead. If you move the business, update both — or remove the kitchen word from the town row and let the coordinate fields decide.
Only towns the theme can place get a pin. A row whose name is unknown to the built-in table and that has no coordinates needs a lookup to succeed. It still appears as a chip and still answers “yes we deliver” — it just has no pin until the place resolves.
How the automatic lookup works

The lookup runs in the customer's browser against two free, key-less services, in order: Photon and then OpenStreetMap Nominatim. Nothing is stored on your store, and you do not need an API key or a billing account.

  • Results are cached in the browser, so a returning visitor causes no new requests for the same place.
  • Requests are queued one at a time, so a long town list never floods the endpoint.
  • The map still renders if both services are unreachable — it falls back to any coordinates you typed.
  • Towns already known to the theme's built-in table are never looked up, so the default list costs nothing.
What a customer can type into the map

Customers are not limited to the towns on your list. Anything they type that is not one of your towns is looked up and plotted on the map, then compared with your delivery circle.

Customer types What the map does
Waukesha (one of your towns)Highlights your existing pin and shows the “we deliver” message. No lookup needed.
53186 (one of your ZIPs)Matches the town that ZIP belongs to.
Oconomowoc (not on your list)Finds the place, drops a ring on it, and reports whether it falls inside your zone.
N64W28381 Hawthorne Rd, Hartland, WIFinds the exact building, not just the town.
ChicagoFinds it, shows the distance from your kitchen, and marks it outside the zone.
asdfghReports that the place could not be found and suggests trying a town or ZIP.
  • The map previews a place while the customer is still typing — one request after a short pause, not one per keystroke.
  • The “inside” or “outside” verdict uses the real distance to your kitchen, so it stays correct after the visitor pans or zooms the map.
  • Your own towns always win. If a listed town and a stray place name match, the listed town is selected.
  • The suggestion list is keyboard operable: ↓/↑ move through towns and the lookup row, Enter selects, Esc closes it. Picking the lookup row is the same as submitting the text.
  • An “outside the zone” answer from the street-map checker also shows the Ask us about your area link, so a customer just beyond your radius still has a way to reach you. Set delivery_contact_url and delivery_contact_label, or leave the URL empty to hide the link.
  • On the plate map, a search tries ZIP first (exact, then prefix), then a town name — exact, then “starts with”, then “contains”. A listed town flies the map to its pin; anything else is geocoded and answered with plate_msg_lookup_in or plate_msg_lookup_out.
  • Submitting an empty field is answered separately — plate_msg_empty on the plate map, and a silent reset to the full zone on the street map.
All of this copy is editable. In Delivery checker: search you can rewrite the lookup messages: delivery_lookup_row (the dropdown row), delivery_lookup_loading, delivery_msg_lookup_yes, delivery_msg_lookup_no and delivery_msg_lookup_fail. Use {place} for the found place, {distance} for its distance from your kitchen, and {query} for what the customer typed. The plate map has the matching plate_msg_lookup_in, plate_msg_lookup_out and plate_msg_lookup_loading fields.
For a production store, coordinates are still best. A lookup is fast but it is a third-party call, and it can fail on a locked-down network. Once you are happy with a place, copy the coordinates from Google Maps into the field and the map stops depending on the network.
Step 3 — Change the map centre and HQ pin

On the product template, select the CM delivery map section.

  • center_lat, center_lng — where the map opens. Put this near the middle of your delivery area, not necessarily your kitchen.
  • zoom — 5 is a whole state, 14 is a few blocks. 9–11 suits a local delivery radius.
  • fit_to_pins — turn on to ignore the zoom and frame every pin automatically. Best when you add or remove towns often.
  • hq_lat, hq_lng, hq_address — the headquarters popup.
  • hq_place — a place name for the HQ instead of numbers, for example Hartland, Wisconsin. Used when the latitude or longitude is blank.
  • geo_country — optional country hint for the automatic lookups.

Each pin block is one delivery town with its own area, lat and lng. Leave the numbers blank and fill Or place name instead, and that pin is looked up automatically. Add, edit or delete blocks to change which towns appear.

Step 5 — Check it
  • Type a town into the checker on each plan page — the yes message names the right town
  • Type a ZIP code that should work — it matches the ZIP column
  • Type a town you removed — you get the not-found message
  • The kitchen dot sits on your real building on the map
  • If you used a place name, the pin lands on the right town once the page finishes loading
  • Every town you listed has a pin, or its coordinates filled in when a lookup failed
  • The delivery ring covers every town you deliver to
  • Footer and contact page show the new address, not the old one
  • Announcement bar and FAQ copy do not name the old city
Plan pages are separate sections. Each plan page (5, 6, 7, 10, 15) has its own copy of the cm-meal-plan-page section, so editing the towns on the 6-meal page does not change the 15-meal page. Repeat step 1–2 on every plan page, or copy the edited JSON template over the others.

Metaobjects

Metaobjects let you keep a long list — 20 meals, 40 FAQs, 30 reviews — outside the theme editor, then point a section at that list. The section setting is called Content source and it always shows the field label from the section schema, for example Meal plans (Metaobject).

How the fallback works
  1. If the Metaobject list selected in the section has entries, the section renders those.
  2. If the list is empty, the section renders its blocks instead.
  3. If both are empty, a short empty-state message is shown in the editor.

Because of this, a section never breaks when you switch modes — the blocks act as the built-in demo content.

Create a definition
  1. Go to Content → Metaobjects → Add definition.
  2. Set the Type to the exact name in the table below (for example meal_plan). The type cannot be changed later.
  3. Add each field with the exact field name and type shown below. Field names become the template accessors, so Short description must be named short_description.
  4. Enable the storefront access for each field you display.
  5. Add entries, set their status to Active, then select the list in the section.

How it works
  1. Each variant of the plan product becomes a meal card, using the variant title as the meal name and the variant image (or a packaged food image) as the photo.

If a name still lands in the wrong place, add the state or country to that one row — Sussex, WI — which removes the ambiguity entirely.

What is still manual:

  • The kitchen. Tick is_kitchen on exactly one delivery_area entry, or set delivery_kitchen_lat/_lng. Nothing can guess which branch cooks the food.
  • Postcodes, only if you want them. postcodes lets a visitor find a town by ZIP. Name search works with it blank.
  • Nothing else. map_x/map_y are accepted for backwards compatibility but no longer read — pin placement comes from geocoding or from latitude/longitude.

The first visitor to a page pays for the lookups: unknown towns are fetched one at a time, spaced to stay polite to the free service. Results are cached in the visitor's browser, so repeat views are instant. To remove the delay entirely, fill latitude/longitude on the delivery_area entries once.

Which town list actually renders

All four delivery styles read one resolved list. The theme stops at the first source that produces at least one town, so an empty list never blanks the map:

  1. delivery_area_list — the metaobject list on the plan product, else the shop-level shared copy.
  2. delivery_towns — the older pipe-delimited product metafield list.
  3. plate_towns / delivery_towns — the theme editor newline list.
  4. The packaged Hartland / Lake Country default list.
An all-empty metaobject list will not shadow your editor list. Entries with a blank name are dropped before the count is checked, so a half-built list falls through to the next source rather than rendering an empty map.

Performance & Accessibility

Performance
  • Images render through image_url + image_tag with explicit widths and sizes, so the browser downloads the smallest usable file.
  • Everything below the fold is lazy-loaded; hero imagery is eager with fetchpriority="high".
  • Scripts are deferred and section-scoped. Maps, carousels and the wheel load only on pages that contain them.
  • Fonts are preloaded and use display=swap.
  • No app scripts, no jQuery, no third-party tracking by default.
Accessibility
  • Semantic landmarks and heading order on every template.
  • Accordions use native <details> / <summary>, so they work with a keyboard out of the box.
  • Visible focus rings (:focus-visible) on buttons, links and form fields.
  • Live regions announce cart and delivery-checker results.
  • Decorative images are hidden from screen readers; content images require alt text.
  • Reduced-motion preference disables scroll animation.
Before launch: run Lighthouse on the home page, one plan page and one product page. Replace demo images with compressed WebP/JPG under 300 KB, and keep the hero at one image rather than a slideshow.
